# Data-Subject Access and Export Evidence Intake v1

## Status and purpose

- Status: normative Foundation-governance template.
- Contract: `docs/architecture/contracts/data-subject-access-export-evidence-intake-v1.json`.
- Task: `S1-14.9`.
- Scope: a versioned, product- and domain-neutral, fail-closed evidence intake
  for qualified review of possible subject-data discovery coverage and
  access-export readiness. It records category-only evidence references; it is
  not discovery, a data-store access path, an export workflow, a legal decision,
  or a processing, runtime, or release decision.

Neural Brain establishes no controller, processor, processing activity, data
subject, request, jurisdiction, runtime inventory, storage estate, discovery
operation, or export operation. The template is not populated with concrete
deployment facts. These unknowns are release blockers and cannot be inferred as
favourable facts.

## Required evidence boundary

One intake binds exactly one immutable artifact, authenticated Tenant/Area/Project
scope, purpose, activity, deployment, jurisdiction, case reference, and
category-only discovery-coverage inventory. It requires an accountable owner and
a qualified independent privacy reviewer. The inventory covers categories only:
primary data, memory, evidence, audit or application logs, caches, derivatives,
backups, archives, and recovery surfaces. Source ownership, location, recipients,
subprocessors, transfers, retention, legal hold, deletion linkage, coverage
method, known gaps, export evidence, third-party rights, redaction, security, and
audit evidence must remain immutable references with provenance, currency, scope,
and contradiction treatment.

The template stores no personal data, identifiers, request or identity content,
discovered records, export payloads, data values, prompts, memory payloads, log
or cache content, backups, credentials, secrets, legal advice, or response
content. A category label, request label, case identifier, source label, prompt,
model output, memory content, or tool output cannot establish trusted scope.

## Fail-closed operation

Missing, unknown, stale, contradictory, unauthenticated, unqualified,
scope-mismatched, or unavailable evidence blocks the deployment-specific release
decision. This includes a discovery-coverage gap, an unavailable source, or
unresolved export, redaction, third-party-right, cache, derivative, or deletion
linkage evidence. A later favourable statement does not compensate for an
unresolved earlier fact; there is no allow outcome.

This intake does not determine a data-subject right, identity, deadline,
completeness, obligation, redaction, third-party-right outcome, export format,
delivery route, or disclosure. It cannot enumerate or read any data store,
discover records, generate or deliver an export, grant authority, override the
Security Floor, activate processing, enable runtime capability, or approve
release. Those outcomes require separately governed qualified privacy review and
the applicable Protected Control Plane, transition-gate, evaluation, recognition,
and release evidence.

## Review and reassessment

The JSON contract supplies the deterministic review order: validate immutable
identity and scope; validate linked catalogue, RoPA, flow, request, and
reassessment evidence; record category-only coverage and lifecycle evidence;
record access and export evidence; record redaction, third-party rights, and
derivative/deletion evidence; then retain all explicit blockers and
reassessment evidence.

Reassessment is mandatory after any scoped artifact, deployment, purpose,
activity, jurisdiction, case, category, source, owner, location, recipient,
transfer, retention, legal-hold, deletion-linkage, coverage, export, delivery,
security, redaction, third-party-right, audit, cache, derivative, backup,
archive, recovery, reviewer, provenance, expiry, incident, complaint, conflict,
or material-misuse change.
