# S1-12.4 model-based property state-machine evidence

## Scope

- Task: `S1-12.4 — Implement model-based and property-based state-machine tests`
- Current implementation boundary: working-memory subset within the Memory Core foundation
- Generated trace budget: exactly 100,000 Hypothesis sequence examples
- Generated model-operation budget: exactly 600,000 sequence steps
- Durable test: `tests/property/test_s1_12_4_memory_state_machine.py`

This evidence exercises the current synchronous `MemoryService` against the
test-only `DeterministicMemoryRepository`. The harness models atomic
persistence, replay receipts, audit IDs, and scoped records; it is not evidence
for PostgreSQL, RLS, the productive Memory Transition Gate, crash recovery, or
live reconciliation. It does not implement, simulate, authorize, or claim a
Goal, Action, Executor, tool, external-effect, or dispatch runtime.

## Model and generated transitions

Every generated trace owns one persistent model and repository state across six
operations. Its sequence starts with one commit so later generated operations
have valid persistent state. Hypothesis then generates five operations over a
63-bit seed space, allowing up to `12^5 = 248,832` operation shapes before
payload and scope values are considered. This produces exactly 100,000 valid
multi-step examples and 600,000 modeled sequence steps. The number is an
executed-example budget, not a claim of 100,000 distinct semantic states.

| Step | Implementation or contract oracle | Expected observed model outcome |
| --- | --- | --- |
| `advance` | `MemoryService` plus deterministic repository | One monotone version and one audit receipt commit |
| `exact_replay` | Repository replay receipt | Original result, no new version or audit receipt |
| `conflicting_replay` | Harness replay-key guard | Denied, no modeled repository-state change |
| `stale_write` | Harness working-memory compare-and-set | Denied, no modeled repository-state change |
| `rollback_write` | Injected harness pre-commit failure | Operation is classified `rolled_back`; modeled records, replay receipts, audit IDs, and failpoint return to the prior snapshot |
| `retry_rolled_back` | Persistent model pending request | Same request commits once, or is denied if an intervening commit made its expected version stale |
| `cross_scope_read` | Authenticated Runtime Context plus harness scope key | Tenant, Area, Project, and Session are changed one at a time; every foreign read is unavailable |
| `incomplete_scope` | Current Security Floor | Missing Project and missing Session are denied independently before harness mutation |
| `authority_na` | Authority contract plus current `MemoryService` surface | Issuer-bound grant resolution and immutable authority snapshots are not integrated here; authority is N/A rather than inferred from scope |
| `dreaming_denied` | Current `MemoryService` | Dreaming remains unavailable and quiescent in the working-memory foundation |
| `reconciliation_required` | Normative Memory Lifecycle contract | Unknown outcomes require reconciliation; no reconciliation runtime is claimed |
| `dispatch_na` | Memory Stage and system-boundary contracts | Dispatch is absent, N/A, and cannot mutate Memory Core state |

After an observed service result, expected exception, or static N/A boundary
check, the test model classifies the model operation as `committed`, `replayed`,
`denied`, `rolled_back`, or `not_applicable`. Multi-request operations record
one outcome per observed request. Reconciliation, authority, and dispatch N/A
are boundary classifications, not runtime request terminal states. Later
operations preserve the complete prior outcome history while acting on the
persistent committed version, last replay receipt, and optional pending retry.

The harness oracle checks after every sequence step that observation and
checkpoint counts equal committed model versions, exactly one scoped
working-memory record carries the monotone version, audit IDs are unique and
commit-count matched, replay receipts are commit-count matched, checkpoint
versions are gap-free, the failpoint is cleared after rollback, and every
harness record retains the authenticated Tenant, Area, Project, and Session
scope. Quiescence snapshots include harness records, audit IDs, replay
receipts, the armed failpoint, and the model's pending-retry reference.

## Invariant coverage

| Required evidence | Generated proof |
| --- | --- |
| Model-operation outcomes | Each generated operation is classified only after its service result, expected denial, rollback observation, or static N/A check. This is model bookkeeping and does not claim a productive protected-state terminal record. |
| Harness quiescence | Replay, stale/conflicting input, independently varied cross-scope reads, incomplete scope, Dreaming denial, reconciliation-only checks, authority N/A, and dispatch N/A preserve the complete harness/replay/failpoint snapshot and pending model state. |
| Authenticated scope | The service admits complete trusted Runtime Context and the harness denies foreign Tenant, Area, Project, and Session dimensions independently. This is Security Floor and test-double scope evidence only. |
| Authority | Issuer-bound grants, snapshots, expiry, revocation, policy binding, and request evidence are not integrated into this `MemoryService` cycle. The generated invariant is fail-closed N/A; separate authority tests remain the applicable component evidence. |
| Harness ledger/replay model | Successful modeled versions, checkpoints, and audit IDs advance together; exact replay is idempotent; changed replay keys and stale versions leave no partial harness state. This does not prove PostgreSQL or Gate atomicity. |
| Reconciliation | The normative contract remains `ready_default = false` and forbids blind retry after an unknown commit outcome. No reconciliation runtime is represented as implemented. |
| Dispatch | Current memory operations contain no dispatch surface; Cognitive Plane external effects are denied. This is negative N/A evidence only. |
