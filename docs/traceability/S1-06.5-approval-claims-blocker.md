# S1-06.5 Approval Claim Consumption Blocker

## Status

`Blocked`. The acceptance criteria require a durable, single-use approval
claim to be atomically prepared and consumed by the owning Memory Transition
Gate. The current repository has no accepted transition-approval lifecycle or
Memory Gate operation that can receive, claim, consume, audit, and reconcile
such evidence in the same PostgreSQL transaction as a protected transition.

This record is deliberately not an implementation claim. It does not add a
claim repository, an approval channel, a prepare/commit facade, a second
protected-state writer, or any enabled Memory Core capability.

## Acceptance criteria and result

| Acceptance criterion | Result | Reason |
| --- | --- | --- |
| Two concurrent claims for one approval have exactly one durable winner. | Blocked | No authoritative persisted approval/claim lifecycle or Gate-owned unique claim operation exists. |
| Replay is rejected. | Blocked | No Gate-owned consumed-state receipt is bound to an approved transition request. |
| Claim is atomically prepared and consumed at commit. | Blocked | The current Gate has no approved prepare/commit contract or parameters for approval evidence, and no migration can safely attach one without that contract. |

## Required prerequisite: S1-06.5a Gate-owned approval-claim contract

Owner: `Neural Brain Protected Control Plane / Memory Transition Gate`.

Before S1-06.5 can start implementation, an accepted, versioned Memory Core
transition-approval contract must define all of the following:

1. The exact Gate-owned lifecycle and durable states for an approval claim,
   including claim identity, request binding, expiry, consumption, failed
   prepare, unknown commit outcome, and authoritative reconciliation.
2. The authenticated source and persistence rules for an approver record. An
   in-process `MemoryOperationApproval` payload is insufficient and must never
   be trusted as a write authority.
3. A single `SECURITY DEFINER` Memory Transition Gate operation that receives
   only identifiers/digests from authenticated context, revalidates current
   authority, policy, approval, scope, checkpoint, and kill-switch state, and
   atomically writes the protected transition, consumed claim receipt, and
   append-only audit evidence.
4. Role grants, RLS/FORCE policies, and direct-write denials that leave the
   Gate as the sole writer of both protected memory state and claim-consumption
   state.
5. The reconciliation rule for crash-before-commit, crash-after-commit, and
   indeterminate outcomes. It must inspect the authoritative receipt by stable
   request/claim identity and never retry a non-idempotent transition blindly.

Expected follow-on artifacts after that contract is accepted:

- a new immutable migration after `0011` for Gate-owned approval and claim
  records plus the extended Gate function;
- an explicit repository port and PostgreSQL adapter that call only that Gate;
- a machine-readable Memory Core contract and runbook for claim reconciliation;
- traceability mapping the lifecycle, sole-writer, atomic-audit, and recovery
  invariants to code and tests.

## Required verification before completion

The implementing change must prove, against a disposable PostgreSQL 18 ledger:

1. two parallel authenticated claim attempts for one approval yield exactly one
   committed winner and one rejected loser, with no partial protected mutation;
2. a second use of the same approval/claim is rejected even after a process
   restart;
3. a rejected, expired, revoked, mismatched, or untrusted approval cannot
   reserve or consume a claim;
4. injected failure before the transaction commit rolls back claim,
   transition, receipt, and audit together;
5. recovery after an unknown outcome reconciles the authoritative receipt and
   does not blindly repeat consumption or the memory transition;
6. direct table writes and non-Gate roles are denied, and every resulting
   record remains Tenant-, Area-, Project-, and Session-bound.

## Unblock condition

S1-06.5 is executable only after the accepted Gate-owned contract above is
versioned and identifies the concrete transition operation, claim state
machine, audit record, recovery authority, database roles, and test fixture.
At that point, S1-06.5 must be re-opened and implemented as one bounded
PostgreSQL Gate change; no standalone claim service is permitted.
